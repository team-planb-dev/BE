## 4. 4D 이후의 최소 TDD 순서

검증 지점은 호출자가 사용하는 `PlanService.makeEditPlanByAi`의 반환 수정안. private 메서드 직접 검증이나 테스트용 공개 메서드 추가 제외. DB preview/확정/취소 및 STOMP 전달은 별도 기존 통합 검증으로 유지.

1. 두 날짜 원본과 범위 밖 변경을 포함한 고정 AI 응답으로 부분 편집의 범위 실패 RED. 실제 AI·검색 응답은 mock으로 대체하되 Java 검증·finish 경로는 실제 실행
2. 원인 단계 확인 후 기존 범위 DTO·validator·PlanService 책임에서 최소 수정. Facade에서는 Service 호출 조립 유지, 새 범용 편집 framework·Flyway 자동 추가 제외
3. 대상 점심 변경과 비대상 날짜/선택 보존을 함께 확인. 전체 응답을 원본으로 되돌려 통과하는 테스트 금지
4. 관광지만 재구성하는 요청에서도 비대상 식사·카페의 보존 검증. 전체 일차 재구성·전체 여행 재구성과 구분
5. 복수 대상·명시적 전체 변경·모호하거나 존재하지 않는 대상·수정 불가 응답·일차/날짜 불일치·중복 선택·후보 복구 실패 회귀. 혼합 요청 “1일차 전체 재구성 + 2일차 점심만 변경”에서는 두 목표 적용·2일차 비대상 선택·3일차 보존을 함께 단언. `preserveOtherDays=false`를 전체 여행의 자유 변경으로 해석하는 회귀 방지
6. 시간 파생 변경과 실제 선택 변경의 평가 분리. 대상 변경으로 필요한 이동·복약 재계산은 4D와 기존 계약을 유지

계약 충돌 시 먼저 보고할 항목: 비대상 날짜의 모든 필드 고정 요구와 기존 직후 날짜 inbound 재계산 계약. 날짜 경계 이동을 무조건 원본으로 덮으면 이동 정합성이 깨질 수 있으므로 해당 예외를 별도 명시. 미정 정책을 프롬프트에 임의 삽입하지 않음.

scope 해석·최초 응답·검증 후·최종 반환의 최소 trace는 고정 테스트 fixture에서 먼저 확보. 실제 실행 기록에는 비밀 키·인증 헤더·불필요한 건강정보 미포함.

### 6-3. 변경

- `PlanEditScope.editTargets`(일차·슬롯 BREAKFAST/LUNCH/DINNER/ATTRACTION/CAFE·장소명·메뉴만 여부). 일차 미지정은 구조화 응답 규격상 `dayNumber=0`. 분류 프롬프트에 일차별 현재 장소 목록 제공
- `PlanEditValidator.editTargets`: 없는 날짜·장소·여러 날짜의 일차 미지정은 AI 편집 호출 전 `EDIT_TARGET_UNCLEAR`. 지목 장소명은 공백 무시 일치 우선, 요청명을 포함한 유일한 저장명(2자 이상)만 허용
- `PlanService.confineToTargets`: 편집 전 골격 유지, 대상 위치에만 같은 종류의 AI 새 슬롯(같은 시작 시각 우선) 배치, 바뀐 장소 다음 구간과 다음 날짜 첫 장소 이동시간 재계산. 재구성·밀도 감소 날짜는 AI 날짜 사용
- `validatePlaces`: 편집 전 원본을 그대로 옮긴 슬롯은 원본 1개당 1회만 보존 검증(`verifyUnchanged`) 후 우선 예약, 새 선택이 겹치면 새 선택만 재선택. 저장 데이터 결함은 원본 유지·로그
- `requireTargetsApplied`: 대상 위치는 모두 바뀌고, 대상 밖 장소는 모두 원본 유지되어야 성공. 아니면 `EDIT_NOT_APPLIED`
- 변경 내역: 대상이 있는 편집은 AI 문구 대신 확정 결과 기준 "N일차 점심: A(메뉴) → B(메뉴)"와 밀도 감소 날짜 고정 문구
