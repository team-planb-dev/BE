# 식약처 식품영양성분DB API의 조회 규격과 1인분 기준

> **2026-09-20 공식 자료 재검증 정정**
>
> 이 문서의 `Z10500=실제 1인분` 해석과 이를 사용한 전역 환산 제안은 기각됐다.
> 공식 명세에서 `Z10500`은 `식품중량`이고, 1회분량은 `DISH_ONE_SERVING`이라는 별도 필드다.
> 아래 서빙 환산 절은 당시 조사 가설 기록이며 구현 근거로 사용하지 않는다.
> 현재 결론과 출처는 `docs/ai/mfds-nutrition-api-verification.md`를 우선한다.

식당 메뉴명으로 영양성분이 조회되지 않는 문제의 원인을 API 규격 쪽에서 확인한 기록이다. 결론부터: **`DB_CLASS_NM`을 넓히는 것은 이 문제의 해법이 아니다.** 그 파라미터는 음식/가공식품을 가르는 축이 아니라 "품목대표냐 상용제품이냐"를 가르는 축이고, 넓히면 가공식품 상용제품 행만 더 들어와 100행 예산을 잡아먹는다. `Z10500`도 존재하지만 공식 의미는 1인분이 아니라 식품중량이므로 전역 환산 근거로 사용할 수 없다.

조사 기준일은 2026-09-20이다. 저장소에 서비스 키가 없어(`src/main/resources/application-common-local.yml:42`가 `${FOOD_NTR_CPNT_KEY}`로만 받는다) **이번 조사에서 실제 API를 호출하지 못했다.** 아래의 규격은 공공데이터포털이 그 페이지에 직접 실어 보내는 Swagger 정의에서 읽은 것이고, 실제 데이터의 성질은 같은 DB에서 나온 표준데이터 미리보기 500행에서 읽은 것이다. 구분해서 적었다.

## 1. 오퍼레이션 규격

정본은 공공데이터포털 `식품의약품안전처_식품영양성분DB정보`다(<https://www.data.go.kr/data/15127578/openapi.do>). 이 페이지의 HTML에는 Swagger 문서가 그대로 들어 있고, 거기서 요청·응답 변수 전체를 읽을 수 있다.

**먼저 버전이 다르다.** 그 페이지가 지금 기술하는 것은 `getFoodNtrCpntDbInq03`이고 host는 `apis.data.go.kr/1471000/FoodNtrCpntDbInfo03`이다. 저장소는 `02`를 부른다(`src/main/java/com/planb/global/client/foodNtrCpnt/handler/FoodNtrCpntHandler.java:33`). 페이지의 등록일은 2024-04-11, 수정일은 2026-09-16이며 문서상 `02`에 대한 언급은 남아 있지 않다. `02`가 언제까지 응답하는지, `03`과 응답 스키마가 어디까지 같은지는 확인하지 못했다.

요청 변수는 `serviceKey`만 필수이고 나머지는 전부 옵션이다.

| 파라미터 | 뜻 | 규격상 샘플값 |
|---|---|---|
| `serviceKey` | 인증키 (URL Encode) | 필수 |
| `pageNo` | 페이지 번호 | `1` |
| `numOfRows` | 한 페이지 결과수 | `3` |
| `type` | 응답 형식, 기본 `xml` | `xml` |
| `FOOD_NM_KR` | 식품명 | `국밥_돼지머리` |
| `RESEARCH_YMD` | 데이터생성일자 | `2017-12-31` |
| `MAKER_NM` | 업체명 | |
| `FOOD_CAT1_NM` | 식품대분류명 | `밥류` |
| `ITEM_REPORT_NO` | 품목제조보고번호 | |
| `UPDATE_DATE` | 데이터수정일자 | `2025-01-23` |
| `DB_CLASS_NM` | 품목대표/상용제품 | `품목대표` |
| `FOOD_OR_NM` | 식품기원명 (`03`에서 추가) | `가정식(분석 함량)` |

**완전일치인지 부분일치인지는 규격에 적혀 있지 않다.** 어떤 파라미터에도 매칭 방식 표기가 없고, 별도의 부분검색 전용 파라미터도 없다. 이름으로 찾는 수단은 `FOOD_NM_KR` 하나뿐이다. 참고로 같은 기관의 구형 API인 식품안전나라 `I0750`은 `DESC_KOR`을 "품목명(부분/LIKE 매칭)"으로 명시하지만(<https://www.foodsafetykorea.go.kr/api/openApiInfo.do?menu_grp=MENU_GRP31&menu_no=656&show_cnt=10&start_idx=1&svc_no=I0750&svc_type_cd=API_TYPE06>), 이 API는 다른 서비스이므로 그대로 옮길 수 없다.

정황은 부분일치 쪽으로 기운다. 공개된 실사용 코드(4절)가 검색어를 포함하는 이름들이 돌아오는 것을 전제로 정렬·중복제거를 하고 있고, 저장소의 헬퍼도 응답이 상위집합이라는 전제로 클라이언트 쪽 `contains` 필터를 둔다(`src/main/java/com/planb/global/client/foodNtrCpnt/helper/FoodNtrCpntHelper.java:56`). 그러나 **실측으로 확정하지는 못했다.** 확정 방법은 6절에 적었다.

`numOfRows`의 상한도 규격에 없다. 저장소는 100을 쓴다(`src/main/java/com/planb/global/client/foodNtrCpnt/dto/request/FoodNtrCpntSearchRequest.java:15`). 개발계정 트래픽 한도는 일 10,000건으로 표기되어 있다.

## 2. `DB_CLASS_NM`이 가르는 축

Swagger의 설명문은 요청·응답 양쪽 모두 `DB_CLASS_NM = "품목대표/상용제품"`, `DB_CLASS_CM = "품목대표/상용제품 코드"`다. 즉 **이 파라미터의 값 공간은 `품목대표`와 `상용제품` 둘이다.** 음식·가공식품·원재료성식품·건강기능식품을 가르는 것은 이 필드가 아니라 `DB_GRP_NM`(데이터구분명)이며, `DB_GRP_NM`은 **요청 파라미터에 없다.** 응답 필드로만 존재한다.

`DB_GRP_NM`의 값 목록은 식의약 데이터포털의 표준DB 검색 화면이 그대로 보여 준다 — 데이터구분: 통합 / 음식 / 건강기능식품 / 가공식품 / 원재료성 식품(<https://data.mfds.go.kr/nsd/obaaa/stdDbSrchRsltList.do>).

규모는 식품안전나라 K-FIND의 목록 API가 응답에 같이 실어 주는 건수 맵에서 확인했다(`/nutrient/general/food/listJson.do`, 2026-09-20 조회, <https://various.foodsafetykorea.go.kr/nutrient/general/food/firstList.do>).

| 구분 | 건수 |
|---|---|
| 가공식품 | 307,028 |
| 음식 | 20,579 |
| 원재료성식품 | 3,605 |
| 합계 | 331,212 |
| 건강기능식품(별도 집계) | 4,380 |

장칼국수·감자옹심이·순두부 같은 한식 한 그릇은 **`음식` 군에 들어간다.** 전국통합식품영양성분정보(음식) 표준데이터 미리보기 500행에서 `김치순두부_바지락`, `김치순두부_돼지고기`, `내장탕`, `꽃게찜`, `김치찜_돼지고기` 같은 행을 직접 확인했다(<https://www.data.go.kr/data/15100070/standard.do>). 이 군의 식품기원명은 가정식(분석 함량) / 외식(분석함량) / 외식(재료량 기반 산출함량) / 외식(프랜차이즈 등 업체 제공 영양정보) / 산업체급식 / 초등학교급식 / 중고등학교급식 일곱 가지였다.

`DB_CLASS_NM`을 아예 빼는 것은 허용된다. 규격상 옵션이고, 공개된 실사용 코드도 이 파라미터를 보내지 않는다(4절). 빼면 `품목대표`와 `상용제품`이 모두 오는데, 전체의 93%가 가공식품이므로 **브랜드 제품 행이 응답을 채운다.** 저장소는 응답을 받은 뒤 `DB_GRP_NM == "음식"`만 남기므로(`src/main/java/com/planb/global/client/foodNtrCpnt/helper/FoodNtrCpntHelper.java:28`) 그 행들은 전부 버려지지만, 버려지기 전에 `numOfRows` 100칸을 먼저 차지한다. **넓히면 음식 행이 1페이지 밖으로 밀려난다.**

음식 군의 행이 `DB_CLASS_NM = 품목대표`를 달고 있다는 것은 규격 문서로는 확인하지 못했다. 저장소의 외부 통합테스트가 그것을 전제로 단언하고 있다 — `품목대표`로 고정한 요청으로 `"막국수"`를 조회해 모든 결과의 `dbGroupName`이 `"음식"`임을 검사한다(`src/test/java/com/planb/integration/external/foodNtrCpnt/FoodNtrCpntHandlerTest.java:74`, `:84`). 이 테스트가 통과한다면 음식 행은 `품목대표`다. 이번 조사에서 실행하지는 않았다(`@Tag("external")`이라 기본 `test`에서 빠진다, `build.gradle:146`).

## 3. 기준량·식품중량·1회분량의 차이

응답의 중량 관련 필드는 의미가 다르다. 공식 Swagger 설명을 기준으로 구분해야 한다.

| 필드 | 공식 설명 | 사용 가능 범위 |
|---|---|---|
| `SERVING_SIZE` | 영양성분함량기준량 | `AMT_NUM*` 값의 기준량 |
| `NUTRI_AMOUNT_SERVING` | 1회 섭취참고량 | 섭취 참고량 |
| `Z10500` | 식품중량 | 식품 또는 제품 전체 중량 |
| `DISH_ONE_SERVING` | 1회분량 참고량 | 1회분량에 관한 별도 필드 |

공식 음식 표준데이터 19,495행에서 `SERVING_SIZE`는 `100g` 13,755행,
`100ml` 5,740행이었다. `DISH_ONE_SERVING`에 대응하는 값은 전부 비어 있었고,
`Z10500`에는 단품·반찬·다인용 조리세트 전체 중량이 함께 들어 있었다.

따라서 `AMT_NUM × (Z10500 / SERVING_SIZE)`는 식품중량 전체 값은 계산할 수 있어도
일반적인 1인분 값은 보장하지 않는다. 현재의 고정 300g도 정확한 근거가 없지만,
`Z10500` 비율로 전역 교체하는 것은 더 안전한 수정이 아니다.

상세 근거와 공식 출처는 `docs/ai/mfds-nutrition-api-verification.md`에 있다.

## 4. 남들은 어떻게 쓰는가

세 건을 찾았다. 셋 모두 **`DB_CLASS_NM`을 반복 호출하거나 넓히는 전략을 쓰지 않는다.**

**`slicequeue/k-mfds-fooddb-mcp-server`** (<https://github.com/slicequeue/k-mfds-fooddb-mcp-server>). `02` 엔드포인트를 그대로 감싼 MCP 서버다. `src/external/mfds/api.ts`가 요청 파라미터 열 개를 1:1로 노출하고, `src/external/mfds/dtos/SearchFoodNutritionRequest.ts`는 `dbClassName` 주석을 `/** 품목대표/상용제품 */`이라고 달아 둔다. 기본값은 빈 문자열이라 **보내지 않는 것이 기본**이다. `validate()`는 `foodNameKr`, `makerName`, `foodCategory1Name`, `itemReportNo` 중 하나만 있으면 통과시킨다. 이름 정규화는 없다. `src/external/mfds/dtos/FoodNutrition.ts`가 `SERVING_SIZE`를 `/** 영양성분함량기준량 */`, `NUTRI_AMOUNT_SERVING`을 `/** 1회 섭취참고량 */`, `Z10500`을 `/** 식품중량 */`으로 매핑한다.

**`yeinariakim/EatsyLog`** (<https://github.com/yeinariakim/EatsyLog>, `js/nutrition-api.js`). 같은 `02` 엔드포인트를 쓰는 식사 기록 앱이다. 요청에 `FOOD_NM_KR`만 싣고 `DB_CLASS_NM`은 보내지 않는다. 대신 응답을 받아 클라이언트에서 처리한다.

- 1인분 중량을 `Z10500`에서 읽는다. 주석은 `"1회 섭취참고량" — 이 음식의 표준 1회 분량 (예: "260.000g" → 260)`이라고 적혀 있고, 코드는 `String(row.Z10500).replace(/[^\d.]/g, "")`로 숫자만 뽑는다. 필드 이름의 라벨은 규격과 어긋난다. 이 제3자 구현의 `Z10500=1인분` 해석은 공식 의미로 정당화되지 않으며, 단위를 버리는 처리도 ml/g 구분을 잃는다.
- `FOOD_REF_NM`(대표식품명)으로 결과를 묶어 브랜드별 중복을 평균으로 합친다.
- 순위를 매길 때 `대표식품명 === 검색어`, `startsWith(검색어)`, `name.includes(검색어)` 순으로 가산점을 준다. **응답에 검색어를 포함하기만 하는 이름이 섞여 온다는 것을 전제한 설계다.**
- 이름이 `카테고리_구체명` 형태인지를 점수에 반영한다. 주석은 `원물/단순 재료는 보통 "카테고리_구체명" 형태가 아니라 짧고 밑줄 없는 이름`이라고 적는다.
- `DB_CLASS_CM` 코드를 `"01" 품목대표 / "02" 상용제품 / "03" 외식`으로 주석해 두었다. **세 번째 값 `03 외식`은 공식 규격에서 확인하지 못했다.** 작성자의 관찰인지 추정인지 판별할 수 없었다.

**`CSE-Sudo/on-care` PR #2104** (<https://github.com/CSE-Sudo/on-care/pull/2104>). API를 직접 부르지는 않고 값을 확정해 저장하는 쪽인데, 1인분 근거를 어떻게 다루는지가 이 문서와 같은 문제를 다룬다. 성분표에 있는 요리는 농촌진흥청 국가표준식품성분표의 조리 상태별 값을 쓰고, 없는 요리는 식약처 음식 DB의 분석값(가정식·외식 분석)을 쓴다. 성분값은 `per_100g` 형식으로 출처 행의 100g당 값을 그대로 적고, 1인 섭취량(`serving_size_g`)은 **따로 근거를 붙여 보관한다** — 가공식품은 「식품등의 표시기준」 [표3]의 1회 섭취참고량, 음식은 가정식 분석 중량 → 급식 → 외식 레시피 분량 순, 원재료는 근거가 없으면 공란. `serving_basis` 필드로 그 근거가 무엇인지까지 남긴다. 즉 **100g 기준값과 1인분 중량을 분리해 저장하고, 1인분 중량에는 출처를 붙인다.**

## 5. 판정

`DB_CLASS_NM`을 넓히는 것은 이름 조회 실패의 해법이 아니다.
음식/가공식품 축은 응답의 `DB_GRP_NM`이고 요청 파라미터가 아니다.
범위를 넓히면 정제 단계에서 버릴 상용제품이 먼저 100행을 채울 수 있다.

2026-09-20 현재 PlanB `02` 경로의 라이브 프로브 결과:

- `칼국수`: 3건, 반환 이름 모두 `칼국수`
- `장칼국수`: 0건
- `검은콩 장칼국수`: 0건

따라서 #56에서는 AI가 조회 가능한 기본 음식명 `칼국수`를 보조 이름으로 전달한다.
Prompt와 Tool 예시도 `검은콩 장칼국수` → `칼국수`로 정정했다.
공식 규격은 매칭 방식을 정의하지 않으므로 이 결과를 전체 API의 완전일치 규칙으로 일반화하지 않는다.

서빙 환산은 별도 문제다. `Z10500`은 1인분이 아니므로 전역 환산에 사용하지 않는다.
제품의 1인분 정책과 신뢰 가능한 출처를 먼저 정해야 한다.

## 6. 확인하지 못한 것

- **`FOOD_NM_KR`이 완전일치인지 부분일치인지.** 규격에 표기가 없고, 서비스 키가 없어 호출로 확인하지 못했다. 저장소에 이미 프로브 테스트가 들어 있다(`src/test/java/com/planb/integration/external/foodNtrCpnt/FoodNtrCpntHandlerTest.java:92`). `"칼국수"` 한 줄을 더해 `./gradlew externalTest`를 돌리면 확정된다.
- **장칼국수·감자옹심이가 음식 군에 존재하는지.** 5절에 적은 이유로 확정하지 못했다. "DB에 없다"고 단정하지 않았다.
- **음식 군의 행이 `DB_CLASS_NM = 품목대표`인지.** 저장소 통합테스트가 전제하고 있을 뿐, 규격 문서로는 확인하지 못했고 테스트를 실행하지도 않았다.
- **`DB_CLASS_NM`의 값이 정말 둘뿐인지.** Swagger 설명문은 `품목대표/상용제품`이라고만 쓰고 enum을 주지 않는다. EatsyLog는 코드 `03 외식`을 주석에 적었는데 출처를 알 수 없었다.
- **`getFoodNtrCpntDbInq02`의 현재 규격.** 포털이 지금 기술하는 것은 `03`뿐이다. `02`가 `DISH_ONE_SERVING`·`FOOD_OR_NM`을 주는지, 언제까지 응답하는지 확인하지 못했다. `03`이 `Z10500`을 주는 것은 규격으로 확인했고, `02`가 주는 것은 두 건의 공개 코드가 실제로 읽고 있는 것으로 확인했다.
- **`Z10500`이 항상 채워지는지, `SERVING_SIZE`가 음식 외 군에서도 100 단위인지.** 표준데이터 미리보기 499행(전부 음식 군)만 보았다. 가공식품·원재료성식품 군의 분포는 보지 않았다.
- **`numOfRows` 상한.** 규격에 없다. 100이 상한이라는 말은 제3자 문서에만 있다.
- 이번 조사에서는 코드를 읽기만 했고 테스트를 실행하지 않았다.
