## 2. 변경 내용

- `FoodNutritionCacheRepository`: Redis 키 `nutrition:food:{조회명}`에 식약처 응답 원본(`FoodNtrCpntResponse.Item` 목록) 저장.
  질환별 평가가 아닌 조회 결과만 저장해 여행자 조건과 무관하게 재사용
- 보존 기간: 결과 있음 30일, 빈 결과 1일(메뉴명 표기 차이 가능성). 오류·timeout은 저장하지 않음
- `NutritionService.lookup`: 캐시 조회 → 미적중 시 식약처 API(건별 15초 상한) → 저장. 표준명 재조회도 같은 경로
- Redis 동기 `RedisTemplate` 호출은 `boundedElastic`에서 실행. WebClient 응답 뒤 처리(Netty event loop)를 막지 않기 위함
- Redis 조회·저장 실패 시 미적중으로 처리하고 API 결과로 평가 계속. 지표 `planb.travel.nutrition.cache{result=hit|miss|error}`

## 4. 실패 2건 — TourAPI 요청 제한

- C4 2·3회차: 모델이 관광지 0개 응답 → AI 단계 검증 correction → 같은 무효 응답 반복(`RESPONSE_REPEATED_INVALID`) →
  `AI_RESPONSE_REJECTED`. 7~10초 만에 종료
- 직전 C4 편집 실행에서 모델 응답에 "경상북도 경주시 관광지 및 음식점 후보 검색이 모두 API 요청 제한(429 Too Many Requests)으로
  실패"가 기록됨. 같은 시각대 생성의 검색 tool도 같은 제한을 받은 것으로 판단
- 측정 직후 TourAPI `searchKeyword2` 호출은 200. 일시적 요청 제한
- **관측 공백:** TourAPI 429가 앱 로그와 지표에 남지 않음. 검색 tool이 실패를 빈 결과로 모델에 넘기고, 모델 응답 문구로만
  원인이 드러남. 후속 과제로 외부 API 오류 코드 계측 필요
- 2026-09-27 기준선의 "4~10초 12/12 `AI_RESPONSE_REJECTED`"도 같은 패턴(검색 후보 없음 → 즉시 거부)이었을 가능성이 있음.
  당시 로그가 없어 확인 불가
