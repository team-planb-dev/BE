### 실패와 안전성 관찰

지역별 통과: 서울 3/3, 부산 3/3, 강릉 3/3, 경주 1/3. 경주 repeat 2·3은 `AI.EXCEPTION.AI_RESPONSE_REJECTED`. stage 기록은 건강 snapshot 성공과 초기 `ai_response` 실패만 존재하며 최종 장소 검증·경로·저장 단계 기록 없음. 이전 P2-4C의 경로 실패와 다른 위치의 실패.

해당 두 실행의 1차 구조화 검증 경고: `tour:2762860`, `교동쌈밥 한정식 (A, B, C)` 메뉴 원본 불일치. 기존 correction 후에도 최종 거부. 강릉 repeat 1·2에도 `tour:623279` 메뉴 불일치 경고가 있으나 최종 생성 성공. 처음부터 검증 오류가 없었다는 의미와 최종 성공을 구분.

거부된 AI 선택 메뉴와 해당 요청의 firstmenu·treatmenu 원문은 보존 raw에 없음. 정확한 잘못된 선택과 원문 분해 오류의 구분은 미확정. 현재 쉼표 구분자는 괄호 안 쉼표도 분할하므로 `교동쌈밥 한정식 (A,B,C)`라는 합성 입력은 세 조각으로 분리. 이는 오프라인으로 확인한 parser 위험이며 실제 실패 원인의 확정 증거는 아님. `·`로 연결된 메뉴의 해석도 별도 검토 대상. 이번 측정 후 운영 코드·단언 완화 없이 결과 보존.

서울 repeat 1의 둘째 날 `가야밀냉면해물칼국수` / `해물손칼국수`에서 `해물` 키워드 적중. 실제 새우 포함 여부는 미확인. proxy 적중을 삭제하거나 재료 안전성이 검증된 것으로 변경하지 않는 판정.

새 Java 계약은 성공 상세의 ID·유형과 firstmenu·treatmenu에서 분리한 메뉴의 정확 일치 검사. 기존 측정기의 양방향 부분 문자열 일치율 60/60은 그 계약의 독립 재증명이 아님. 원본 상세가 없어 raw만으로 strict 출처를 재계수할 수 없는 한계. 또한 메뉴 출처 일치는 실제 재료·영양 정확성·영업 여부의 증명이 아님.

복약 검사는 점심 종료 30분 후, 기존 비식사 슬롯 충돌 이동, 10분 체류, 동일 시각 동행인 복약 설명 병합·MEDICATION_SCHEDULE 태그·장소 필드 부재의 fixture 계약 확인. raw `saved=false`는 사용자 확정 전 상태이며 DB 미저장 의미가 아님. 성공 10회 persistence stage 성공 기록과 원자성 회귀 테스트는 존재하나 이번 배치의 DB 행 전체 독립 감사는 미실행.

### 채택 판정과 다음 조사

### 문제의 실행 경로

1. `PlanTourismTool.getRestaurantDetail`은 상세 문자열 원본을 AI에 반환하고, 같은 응답을 `PlaceCandidateContext.recordRestaurantDetail`에 기록.
2. Java 정규식은 괄호 깊이를 고려하지 않고 모든 쉼표를 분리. 허용 값은 `교동쌈밥 한정식 (A`, `B`, `C)`의 3개.
3. `restaurantMenuFailure`의 정확 일치 검사에서는 원문 전체가 허용 목록에 없어 거부. 반대로 독립 메뉴의 근거가 없는 `B` 조각은 승인.
4. 오류 메시지는 `List.toString()`으로 구성. 세 조각을 쉼표·공백으로 다시 연결하면 `[교동쌈밥 한정식 (A, B, C)]`로 출력되어 원문 한 개의 목록처럼 보이는 상태.
5. correction은 이 오류 메시지와 이전 전체 응답을 AI에 전달. 허용 항목의 실제 경계를 알 수 없는 인터페이스. 실제 경주 2건에서는 동일 무효 응답 반복으로 종료.
6. `MissingSlotCompleter`도 같은 분해 목록의 첫 미사용 메뉴를 선택. 경주 repeat 1의 잘린 아침 메뉴는 이 단계의 로그와 성공 raw에서 확인.

따라서 이번 문제는 단순한 AI 메뉴 지어내기로 분류할 수 없는 상태. Tool이 보여 주는 메뉴 단위와 Java가 승인하는 단위가 다른 계약 충돌. 동일한 모호한 목록이 correction에도 전달되는 구조. 후보 ID·응답 성공 코드·contentTypeId 검사에는 이번 증거상 불일치 없음.

### 가설별 판정

- H1 — 괄호 안 쉼표 오분해: **결함 확정**. 실제 클래스에서 현재 API 원문 입력 시 3/3 동일 거부. 실제 성공 raw의 잘린 메뉴로 실행 영향도 확인.
- H2 — AI가 원문과 다른 최종 메뉴를 선택: **미확정**. foodName Tool 인자는 원문 형태이나 최종 거부 JSON의 menuName은 미보존. 두 요청의 오거부를 확정하려면 해당 값의 보존 필요.
- H3 — correction 안내의 모호성: **구조적 문제 확인**. 목록 경계 소실 재현, 실제 동일 응답 반복 확인. 안내만 수정하면 회복되는지는 미실험.
- H4 — 상세 ID·유형·헤더 오류: **현재 증거와 맞지 않음**. 해당 경고는 출처가 이미 확인된 메뉴 목록의 정확 일치 실패 경로. 키 인증 실패나 다른 음식점 상세 거부 경로와 구분.

기존 메뉴 출처 proxy가 60/60이었던 결과도 품질 해결의 증거가 아님. 기존 계수기는 괄호·쉼표로 나눈 항목과 양방향 포함 관계를 허용하여 이런 잘린 메뉴를 잡지 못하는 구조. 생성 성공률과 메뉴 출처 정확성을 따로 검증해야 하는 실제 사례.

### 수정 시작점과 필요한 회귀 계약

수정 시작점은 shared 메뉴 원본 분해이며, AI 판단 분할이나 Hikari·가상 스레드 변경이 아님. 기존 모듈에서 괄호 안 설명을 보존하고 검증된 최상위 목록 구분자만 분해하는 정책 검토. 모든 원문을 통째로 추가 허용하는 방식은 여러 단품 목록까지 하나의 메뉴로 승인할 수 있으므로 제외.

correction에는 허용 메뉴 경계를 JSON 배열 등 명확한 표현으로 전달하고, 거부된 선택값을 포함하는 최소 진단값 검토. 생성·재선택·Java 보충이 동일한 메뉴 목록을 사용하도록 유지. 잘린 조각·임의 부분 문자열 승인 금지.

회귀 검증은 현재 교동쌈밥 원문 전체 보존, `B`·`C)`·잘린 `(A` 거부, 괄호 밖 단품 목록 분리, 기존 HTML br·공백·빈 메뉴·다른 상세 ID 처리 유지, 동일 메뉴 중복 방지, 정상 슬롯 보존, correction의 허용 항목 경계 전달. 운영 수정과 품질 재측정은 이번 원인 분석 이후 단계.
