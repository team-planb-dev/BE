# P2-4 생성·재선택 메뉴 계약 정렬

작성일: 2026-10-10. Issue #177. 기준: dev `127e1a2`(운영 코드 P2-4A). B/C 독립 실험 코드 미포함. dev 전달만 허용, main 동기화 제외.

## 목표와 범위

장소 ID 복원과 별개로 음식점 메뉴의 출처를 검증하고, 생성·재선택·Java 식사 보충에서 같은 상세 원본을 사용한다. 프레임워크나 DTO 교체, Tool 축소, 영업시간 해석, 날짜별 fan-out, 경로 복구 변경은 이번 범위 밖이다.

B의 부산 실패는 후보 존재·메뉴 포함·식사 자격을 한 메시지로 표시한 관측 결과다. 세 조건 중 실제 원인은 미확정이며 이 수정의 직접 원인으로 단정하지 않는다. A 코드에서 확인된 공백은 음식점 메뉴 원본 검증 부재다.

## 구조와 계약

1. `PlaceCandidateContext`가 요청별 후보 ID와 상세 메뉴 목록을 보관한다. 상세 item의 contentid·contenttypeid는 검색한 TourAPI 음식점과 일치해야 한다. 성공 코드 0000·00 이외(헤더·코드 누락 포함), 다른 ID·유형, 빈 결과를 정상 메뉴 근거로 사용하지 않는다.
2. 대표 메뉴 firstmenu를 먼저 나열하고 treatmenu의 실제 메뉴도 추가한다. 쉼표·슬래시·세미콜론·파이프·줄바꿈·HTML br만 목록 구분자로 사용한다. 앞뒤 공백만 제거하고 부분 문자열·유사도·임의 별칭은 승인하지 않는다.
3. `PlanTourismTool.getRestaurantDetail`의 이름·인자·반환 타입은 유지하며 성공한 상세를 컨텍스트에 기록한다. 모델과 Java가 같은 원본에서 선택할 수 있도록 Tool 설명과 생성·재선택 프롬프트에 계약을 명시한다.
4. 초기 생성 callback과 최종 PlanPlaceResolver.validate(재선택·보충·편집·재구성 공통)는 공통 메뉴 검사로 후보 없음·유형 오류·상세 미확인·메뉴 없음·원본 불일치를 구분한다. 기존 생성 correction과 슬롯 재선택 횟수는 늘리지 않는다. 재선택의 새 전체 correction을 추가하지 않고 기존 PlanService 슬롯 재선택 루프를 사용한다.
5. `MissingSlotCompleter`는 같은 상세 파싱을 사용하여 대표 메뉴 우선의 첫 미사용 메뉴를 선택한다. 첫 메뉴가 이미 사용됐을 때 실제 다른 메뉴를 사용할 수 있으며, 빈 원본이나 다른 식당 상세에서는 메뉴를 만들어내지 않는다.
6. 기존 식사 유형·시각 규칙은 PlanPlaceResolver와 MealSlotPolicy 유지. 임의 영업시간 해석이나 B의 전 후보 영업시간 완화 규칙은 도입하지 않는다.
7. 최초 생성에서 실제 메뉴 원문을 복원하되 메뉴 선택 자체는 바꾸지 않는다. 재선택 결과도 같은 메뉴 계약으로 검사하고 실패 시 기존 검증·복구 흐름으로 전달한다. 기존 편집 DTO와 정상 슬롯 유지·최종 검증·원자적 저장 보존. 상세 출처 검사는 tour:·유형 39에 적용하며 카카오 FD6는 기존 호환성 유지, 이번 출처 검증 범위 밖. verifyExisting의 저장된 슬롯에는 신규 상세 조회 요구 없음.

상세 메뉴와 보충 조회 완료 표시는 전역 상태에 두지 않으며 새 요청·후보 초기화 시 제거한다. 정상 반환 뒤 메뉴 원본을 확인하지 못한 조회도 같은 요청의 보충 과정에서 반복하지 않으며, 이 조회 완료 표시는 메뉴 출처 증거가 아니다. 조회 예외는 완료로 기록하지 않아 기존 후속 보충의 재시도 동작을 유지한다. 오류 뒤 기존 상세를 유지할지 여부는 동일 요청에 이미 성공한 같은 후보 상세가 있는지 기준으로 결정한다. 다른 ID 또는 실패 응답으로 성공한 원본을 덮어쓰지 않는다.

## Grilling 자동 권장 채택 기록

- Round 1 기준 코드: 채택 P2-4A. 미채택 B/C 누적 금지. 신규 메뉴 ID·동적 enum 대신 기존 candidateId와 menuName 사용.
- Round 2 메뉴 근거: firstmenu와 treatmenu 모두 실제 원본으로 허용, 대표 메뉴 우선. 성공 응답의 일치 ID만 기록. 표준 음식명은 영양 조회용이며 메뉴 출처 근거에서 제외.
- Round 3 검증 위치: 생성 응답의 기존 validation callback과 재선택의 공통 메뉴 검사. 이미 있는 슬롯 복구 재사용. 예산 증대·추가 모델 호출 경로 금지.
- Round 4 조회 실패: 거부 또는 다른 후보 선택. 필수 슬롯 삭제·메뉴 추정으로 성공 처리 금지. 상세 조회 오류의 기존 전파·후보 제외 정책 유지.
- Round 5 확인 seam: 초기 생성 결과·재선택 결과·Java 보충 결과 및 요청 컨텍스트의 메뉴 출처 계약. 기존 사용자 승인(사용자에게 보이는 생성 결과, 잘못된 ID 거부, 편집 경로 유지)과 자동 권장 채택 지시 적용.
- 프론티어: 구현 전 미결정 정책 없음. 실제 API 실측 12회 승인은 별도 요청 중이며 승인 전 실행 금지.

## TDD와 검증

한 행동씩 RED/GREEN. 알려진 원본 메뉴 허용, treatment 메뉴 허용, 같은 이름의 다른 식당 메뉴 거부, 상세 조회 누락·다른 ID·오류 코드 거부, 빈 대표 메뉴 fallback, 목록·공백·부분 문자열, 요청 초기화·동시 요청 격리, 초기 생성·재선택 일치, deterministic 보충, 정상 편집 보존을 확인한다.

무료 단위·통합·stub 테스트는 출처 계약과 기존 기능 유지의 증거다. 실제 모델 품질은 별도 승인한 생성 12회에서 비교하며, 무료 테스트 성공을 제품 품질 개선으로 주장하지 않는다. Review-loop 2회 이상, 최종 9/10 이상 및 Critical/Important 0건.

## 후속 순서

1. 현재 선택 계약 정렬
2. 실패 종류별 복구와 정상 슬롯 보존
3. Java 필수 일정 골격 도입 필요성 판단
4. AI 결정 의존 관계 분리 필요성 판단

각 단계의 실패 증거와 개선 결과를 확인한 뒤 다음 설계로 진행한다. 기존 계획의 P2-5A·P2-5B 명칭과 위 진행 순서는 구분한다.

## 한계

TourAPI 목록의 모호한 표기는 source 검증 실패를 늘릴 수 있다. 등록 메뉴 일치는 실제 재료·알레르기 안전성이나 현재 영업을 보장하지 않는다. 경주 경로 실패는 이 수정의 해결 범위 밖이다.
