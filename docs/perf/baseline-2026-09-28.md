# Phase 3 — Travel 일정 생성 처리량 기준선

- Issue: #105
- 애플리케이션 기준 commit: `14e53770a3dc960e95e3184e843fb0e6eec636e1`
- 측정일: 2026-09-28
- 범위: `POST /api/v1/travel/add-with-recommend`

## 1. 목적

Phase 4 최적화 후보를 평가하기 전에 현재 Travel 일정 생성 경로의 성공률, 처리 시간,
처리량과 자원 상태를 같은 조건에서 반복 측정한다. 실제 OpenAI와 외부 API는 호출하지 않고
Phase 2의 결정적 로컬 스텁을 사용한다.

이 측정은 로컬 기준선이다. Railway 운영 환경의 최대 처리량이나 장애 임계점을 의미하지 않는다.

## 2. 실행 환경

| 항목 | 값 |
|---|---|
| Java | 21.0.2 |
| Spring Boot | 4.0.2 |
| 애플리케이션 | 단일 로컬 프로세스, `loadtest` profile |
| 부하 도구 | 공식 `grafana/k6` Docker image, digest `sha256:e66db15b860113878fa74670e31f5e274830b7b6e42c8bff28b2f2d86a257603` |
| MySQL | 8.4, disposable Docker container |
| Redis | 7.2, disposable Docker container |
| OpenAI | `OpenAiChatCompletionStub`, `localhost:18081` |
| 외부 API | `ExternalHttpStubServer`, `localhost:18080` |
| 테스트 일정 | 서울 종로구, 1박 2일, 하루 관광지 2개 |

실제 API key, 외부 네트워크와 유료 요청은 사용하지 않았다. DB와 Redis 데이터도 측정용
container를 종료하면 폐기된다.

## 3. 시나리오

스크립트는 `src/test/k6/travel-plan.js` 하나만 사용한다.

### 3-1. 준비

`setup()`에서 한 번만 다음을 수행한다.

1. 측정용 사용자 생성
2. 로그인과 JWT 획득
3. 최소 건강정보를 가진 동행인 생성
4. 동행인 `healthId` 조회

각 일정 생성 응답은 다음 조건을 모두 만족해야 성공이다.

- HTTP 200
- 공통 응답의 `success=true`
- 이틀 일정 존재
- 각 날짜에 관광지 2개 존재

### 3-2. Smoke

| 항목 | 값 |
|---|---|
| Executor | `shared-iterations` |
| VU | 1 |
| 반복 | 3회 |
| 결과 | 3/3 성공 |
| 일정 생성 평균 | 86.24 ms |
| p50 | 68.52 ms |
| p95 | 141.95 ms |
| 최대 | 150.11 ms |

최초 cold smoke에서는 첫 요청의 애플리케이션 초기화 비용으로 최대 752.28 ms와 p95 686.53 ms가
관찰됐다. 이후 요청은 100 ms 안쪽이어서 최종 기준선은 초당 5건으로 시작하고, 미리 할당한 VU
5개와 최대 VU 10개를 두었다. 위 표는 응답 필드 검증을 보강한 최종 warm smoke 결과다.

### 3-3. 처리량

| 항목 | 값 |
|---|---|
| Executor | `constant-arrival-rate` |
| 요청률 | 5 iteration/s |
| 측정 시간 | 30초 |
| `preAllocatedVUs` | 5 |
| `maxVUs` | 10 |
| `gracefulStop` | 10초 |
| 중단 조건 | 일정 성공률과 check 성공률이 100% 미만이면 실패 |

응답 종료 후 다음 요청을 보내는 closed model 대신 open model을 사용해 느린 응답이 요청률을
자동으로 낮추는 coordinated omission을 피했다. 일정 생성 함수에는 `sleep`을 넣지 않았다.

## 4. 결과

같은 애플리케이션과 container를 유지한 채 최종 시나리오를 두 번 실행했다.

| 지표 | 실행 1 | 실행 2 | 실행 2 기준 편차 |
|---|---:|---:|---:|
| 완료 일정 | 151 | 150 | -0.66% |
| 달성 처리량 | 4.967/s | 4.952/s | -0.30% |
| 성공률 | 100% | 100% | 0%p |
| 실패 check | 0 | 0 | 0 |
| `dropped_iterations` | 0 | 0 | 0 |
| 평균 | 48.76 ms | 47.47 ms | -2.65% |
| p50 | 45.07 ms | 43.84 ms | -2.73% |
| p95 | 68.03 ms | 71.85 ms | +5.62% |
| p99 | 118.09 ms | 94.55 ms | -19.93% |
| 최대 | 171.40 ms | 152.31 ms | -11.14% |

두 실행의 k6 `vus` 최대값은 1이었다. 설정상 사용할 수 있는 VU는 5개였지만 이 부하에서는
추가 VU가 필요하지 않았고 드롭도 발생하지 않았다.

### 4-1. 애플리케이션 자원 snapshot

각 실행 종료 직후 `/actuator/prometheus`에서 다음 값을 확인했다.

| 지표 | 실행 1 | 실행 2 |
|---|---:|---:|
| Hikari active | 0 | 0 |
| Hikari idle | 10 | 10 |
| Hikari pending | 0 | 0 |
| HTTP active | 0 | 0 |
| JVM live threads | 62 | 62 |
| JVM used memory 합계 | 297,703,400 bytes (약 283.9 MiB) | 368,825,776 bytes (약 351.7 MiB) |
| process CPU usage | 0.01164 | 0.00850 |
| system CPU usage | 0.34730 | 0.32033 |

이는 종료 직후 snapshot이며 측정 구간의 최대값은 아니다. 이번 부하에서는 대기 connection이나
드롭이 없어 Phase 4 판단에 필요한 최소 상태만 기록했다. 자원 최대값과 시계열은 Prometheus
수집기가 연결된 뒤 측정한다.

### 4-2. 로그

최종 실행 구간의 로그를 초 단위로 집계했다.

| 항목 | 값 |
|---|---:|
| 정상 상태 | 25 lines/s |
| 실행 구간 최대 | 26 lines/s |
| 애플리케이션 시작 구간 최대 | 30 lines/s |

일정 한 건마다 `TourismTool` 호출 1줄과 `MissingSlotCompleter` 보정 4줄이 남아 정상 상태가
5 requests/s × 5 lines/request = 25 lines/s로 나타났다. Railway에서 관찰한 로그량은 네트워크와
실제 AI 응답이 포함되므로 이 로컬 값으로 직접 대체할 수 없다.

있어 repository에는 커밋하지 않았다.

## 6. 해석 범위

- 초당 5건에서는 성공률 100%, 드롭 0건, p95 약 80 ms로 두 실행이 안정적이었다
- 이 결과만으로 최대 처리량, Railway 자원 한계, 실제 외부 API 지연을 판단할 수 없다
- 스텁은 고정된 정상 응답을 빠르게 반환하므로 OpenAI와 외부 API의 실제 latency 분포를 재현하지 않는다
- Phase 4에서는 이 기준선과 운영 지표를 함께 사용해 병목 가설을 분류한다
- 더 높은 요청률의 breakpoint 탐색, 장시간 soak test와 Prometheus 시계열 수집은 이번 Issue 범위가 아니다
